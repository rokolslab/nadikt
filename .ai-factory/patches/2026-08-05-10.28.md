# NFKC span mapping for decomposed Unicode normalization

**Date:** 2026-08-05 10:28
**Files:** src/nadikt/domain/text/normalization.py, benchmarks/asr/manifests.py, benchmarks/asr/datasets/ru_coding_terms.v1.json, tests/unit/test_text_normalization.py, tests/contract/test_ru_coding_terms_dataset.py
**Severity:** medium

## Problem

Domain text normalization claimed `NFKC`/`casefold` matching, but a decomposed Unicode input such as `e` plus combining accent did not match a precomposed variant. Manifest validation also accepted `expected_coding_terms.accepted_variants` duplicates that were distinct bytes but equivalent after `NFKC`/`casefold`.

## Root Cause

The normalizer built its comparable text by normalizing one character at a time. That preserved compatibility expansions like fullwidth Latin, but missed canonical composition across adjacent base characters and combining marks. Manifest duplicate validation used byte-level `set(variants)` instead of the same normalized comparison semantics used by domain matching.

## Solution

Changed `_comparable_with_index_map()` to normalize base-character plus following combining marks as a cluster and keep start/end maps back to the original text. This preserves original replacement spans while allowing precomposed and decomposed forms to match. Added normalized duplicate detection for public manifest variants and removed a redundant `GitHub Actions` metadata variant that became duplicate under the stricter rule.

## Prevention

- When code promises Unicode normalization semantics, regression tests should include both compatibility forms and canonical decomposed forms.
- Span-preserving matchers should keep both start and end maps, not only a single original index per comparable character.
- Public metadata validators should use the same normalized key semantics as the runtime/domain matching path.
