# «Надикт» (Nadikt)

## Стратегия разработки для Windows и Ubuntu

**Дата:** 26 июля 2026 г.  
**Статус:** согласовано  
**Основная среда разработки:** Ubuntu  
**Основной целевой продукт MVP:** Windows 10/11 x64  
**Перспективная платформа:** Ubuntu

## 1. Принятое решение

Разработка проекта «Надикт» начинается на Ubuntu, где расположен основной программный стек:

- OpenAI;
- AI Factory;
- инструменты разработки и тестирования;
- основной рабочий репозиторий проекта.

При этом первым законченным продуктом должна стать версия для Windows 10/11.

Принята следующая последовательность:

> Общее ядро на Ubuntu → ранний Windows-прототип → Windows MVP → Ubuntu-версия.

Разработка полноценного законченного приложения сначала для Ubuntu с последующим переносом на Windows не предусматривается.

## 2. Обоснование

Большая часть логики программы не зависит от операционной системы и может удобно разрабатываться и тестироваться на Ubuntu:

- захват и предварительная обработка звука;
- VAD;
- сегментация длинной записи;
- подключение ASR-движков;
- распознавание речи;
- сборка текста из сегментов;
- пользовательский словарь;
- команды форматирования;
- нормализация текста;
- конфигурация;
- журналирование;
- автоматические тесты.

Однако критически важные функции MVP зависят от Windows:

- глобальная горячая клавиша;
- определение активного окна и поля ввода;
- безопасная вставка текста;
- работа с буфером обмена;
- взаимодействие с защищёнными полями;
- плавающее окно без перехвата фокуса;
- системный трей;
- автозапуск;
- работа в Word, браузерах и 1С;
- Windows-установщик;
- удаление и обновление программы.

Эти функции должны проверяться на Windows с раннего этапа проекта. Их нельзя откладывать до завершения общей или Ubuntu-версии.

## 3. Основные принципы

### 3.1. Общее ядро

Основная бизнес-логика и обработка аудио должны быть независимы от операционной системы.

### 3.2. Платформенные адаптеры

Операционно-зависимые функции реализуются через отдельные адаптеры:

- `WindowsAdapter`;
- `LinuxAdapter`.

### 3.3. Ранняя проверка Windows

После создания минимально работоспособного ядра должен быть собран Windows-прототип полного пользовательского цикла.

### 3.4. Единый репозиторий

Код Windows- и Ubuntu-версий размещается в одном репозитории. Создание независимых репозиториев для каждой операционной системы не предусматривается.

### 3.5. Git как средство передачи изменений

Изменения между Ubuntu, Windows и системой автоматической сборки передаются через Git.

Работа с общей копией исходного кода на сетевом диске вместо Git не является основным способом разработки.

### 3.6. Сборка на целевой ОС

Финальные Windows-сборки и установщики создаются в Windows-среде или на Windows CI.

Финальные Ubuntu-пакеты создаются в Ubuntu-среде.

Кросс-компиляция Windows-установщика на Ubuntu не должна быть единственным способом выпуска Windows-версии.

## 4. Этап 1. Общее ядро на Ubuntu

### 4.1. Цель

Получить работоспособное общее ядро распознавания речи без зависимости от Windows-интерфейса.

### 4.2. Состав работ

На Ubuntu реализуются:

- запись звука с выбранного микрофона;
- короткий предварительный аудиобуфер;
- VAD;
- деление длинной записи на сегменты;
- защита от пропусков и повторов на границах сегментов;
- единый интерфейс ASR-движка;
- адаптер GigaAM;
- адаптер faster-whisper;
- возможность последующего подключения T-one;
- сборка распознанного текста;
- локальная пунктуация и нормализация;
- пользовательский словарь;
- правила замен;
- голосовые команды форматирования;
- техническое журналирование без аудио и распознанного текста;
- модульные и интеграционные тесты;
- сравнительный тест моделей.

### 4.3. Минимальный результат

Первый прототип может работать из командной строки:

```text
начало записи
→ получение аудио
→ остановка записи
→ сегментация
→ распознавание
→ вывод готового текста
```

На этом этапе не обязательны:

- системный трей;
- глобальная горячая клавиша;
- плавающее окно;
- автоматическая вставка;
- Windows-установщик.

### 4.4. Критерии завершения этапа

Этап считается завершённым, если:

1. программа записывает звук с микрофона;
2. длинная запись корректно делится на сегменты;
3. GigaAM распознаёт русскую речь;
4. второй движок может быть подключён через общий интерфейс;
5. текст собирается без пропусков и повторов;
6. пользовательский словарь применяется к результату;
7. процесс работает без подключения к интернету;
8. подготовлен сравнительный отчёт по моделям;
9. общая логика покрыта автоматическими тестами.

## 5. Этап 2. Ранний Windows-прототип

### 5.1. Цель

Как можно раньше проверить полный пользовательский сценарий на целевой операционной системе.

### 5.2. Минимальный вертикальный сценарий

```text
глобальная горячая клавиша
→ запись с микрофона
→ локальное распознавание
→ помещение текста в буфер обмена
→ вставка в активное поле
```

### 5.3. Обязательные функции прототипа

- запуск и остановка записи глобальной горячей клавишей;
- использование общего ядра;
- работа минимум с одним локальным ASR-движком;
- сохранение целевого окна;
- помещение результата в буфер обмена;
- вставка текста в активное приложение;
- уведомление об ошибке;
- сохранение текста при неудачной вставке;
- отмена записи без вставки.

### 5.4. Проверяемые приложения

Прототип должен быть испытан как минимум в:

- Блокноте;
- Microsoft Word;
- браузерном текстовом поле;
- 1С;
- многострочном текстовом поле;
- приложении, не принимающем обычную вставку через `Ctrl+V`.

### 5.5. Проверяемое оборудование

Основные испытания производительности выполняются на целевом ПК:

- Intel Core i3 10-го поколения;
- 16 ГБ оперативной памяти;
- без дискретной видеокарты;
- Windows 10 или Windows 11 x64;
- системный SSD.

### 5.6. Критерии завершения этапа

Этап считается завершённым, если:

1. горячая клавиша работает при свёрнутом приложении;
2. запись начинается без заметной потери первого слова;
3. текст распознаётся локально;
4. кириллица и переносы строк корректно вставляются;
5. текст не вставляется в другое окно при смене фокуса;
6. прежнее содержимое буфера обмена не теряется;
7. при ошибке вставки результат остаётся доступен пользователю;
8. программа не создаёт параллельные сеансы записи;
9. получены фактические показатели скорости, ОЗУ и загрузки процессора.

## 6. Этап 3. Windows MVP

### 6.1. Цель

Получить законченную автономную утилиту для Windows 10/11.

### 6.2. Состав Windows MVP

В MVP добавляются:

- полупрозрачное плавающее окно;
- визуализация уровня голоса;
- отображение состояний записи и распознавания;
- системный трей;
- автозапуск;
- переназначаемая горячая клавиша;
- режим «нажал/нажал»;
- дополнительный push-to-talk;
- отключаемые звуковые сигналы;
- выбор микрофона и проверка уровня;
- выбор режима распознавания;
- пользовательский словарь;
- команды форматирования;
- безопасная вставка;
- восстановление буфера обмена;
- режим «только в буфер обмена»;
- восстановление последнего результата без постоянной истории;
- автономные модельные пакеты;
- проверка целостности моделей;
- настройки;
- самодиагностика;
- Windows-установщик;
- стандартное удаление программы.

### 6.3. Критерии завершения этапа

Этап считается завершённым после выполнения:

- функциональных требований основного ТЗ;
- критериев приёмки Windows;
- требований автономности;
- испытаний на целевом ПК;
- установки без интернета;
- проверки удаления программы;
- проверки отсутствия аудио и текста после удаления;
- проверки лицензий и состава сторонних компонентов.

## 7. Этап 4. Ubuntu-версия

### 7.1. Цель

На основе общего ядра создать полноценную версию «Надикта» для Ubuntu.

### 7.2. Платформенные функции Ubuntu

Реализуются:

- `LinuxAdapter`;
- глобальные горячие клавиши;
- работа в Wayland и X11 в согласованном объёме;
- вставка текста в активное приложение;
- буфер обмена;
- системный трей;
- автозапуск;
- плавающее окно;
- Linux-уведомления;
- пакет `.deb`, AppImage или иной согласованный формат.

### 7.3. Ограничения

Способы глобального перехвата клавиш и вставки текста в Ubuntu могут различаться в зависимости от:

- Wayland или X11;
- GNOME или KDE;
- доступных порталов рабочего стола;
- разрешений на виртуальный ввод;
- установленных системных компонентов.

Эти различия должны быть скрыты внутри `LinuxAdapter` и не влиять на общее ядро.

## 8. Предлагаемая структура репозитория

```text
nadikt/
├── core/                   # общая логика приложения
├── asr/
│   ├── interface/          # единый контракт ASR
│   ├── gigaam/             # адаптер GigaAM
│   ├── faster_whisper/     # адаптер faster-whisper
│   └── tone/               # перспективный адаптер T-one
├── audio/
│   ├── capture/            # захват звука
│   ├── vad/                # определение речевой активности
│   └── segmentation/       # сегментация длинной записи
├── text_processing/
│   ├── dictionary/         # пользовательский словарь
│   ├── commands/           # команды форматирования
│   └── normalization/      # нормализация текста
├── platform/
│   ├── interface/          # контракт платформенного адаптера
│   ├── windows/            # WindowsAdapter
│   └── linux/              # LinuxAdapter
├── ui/                     # общий пользовательский интерфейс
├── tests/
│   ├── unit/
│   ├── integration/
│   ├── windows/
│   └── linux/
├── benchmarks/             # тесты моделей и производительности
├── model_packs/            # метаданные модельных пакетов
├── packaging/
│   ├── windows/
│   └── linux/
└── docs/
```

Фактическая структура уточняется после выбора языка программирования и пользовательского фреймворка, но разделение общего ядра и платформенных адаптеров является обязательным.

## 9. Организация сборок

### 9.1. Ubuntu

На Ubuntu выполняются:

- разработка основной части проекта;
- локальные тесты;
- тестирование общего ядра;
- тестирование ASR-движков;
- статический анализ;
- подготовка исходного кода;
- будущая сборка Linux-пакетов.

### 9.2. Windows

На Windows выполняются:

- сборка Windows-приложения;
- сборка установщика;
- испытание системной интеграции;
- испытание микрофона;
- проверка горячих клавиш;
- тестирование вставки;
- проверка совместимости с Windows 10/11;
- проверка производительности;
- подписание установщика при наличии сертификата.

### 9.3. Автоматическая сборка

Рекомендуется предусмотреть CI для:

- запуска общих тестов на Ubuntu и Windows;
- сборки Windows-артефакта;
- проверки зависимостей;
- контроля версий модельных пакетов;
- формирования контрольных сумм;
- публикации тестовых сборок.

CI не заменяет ручное тестирование микрофона, горячих клавиш, плавающего окна и вставки в реальные Windows-приложения.

## 10. Что не следует делать

Не рекомендуется:

- сначала полностью завершать Ubuntu-приложение и только затем начинать Windows-порт;
- смешивать общее ядро с Windows API;
- смешивать общее ядро с Wayland/X11 API;
- создавать отдельную реализацию распознавания для каждой ОС;
- держать разные версии бизнес-логики в Windows- и Ubuntu-ветках;
- откладывать тестирование Windows до конца проекта;
- считать успешную сборку подтверждением работоспособности горячих клавиш и вставки;
- использовать кросс-компиляцию на Ubuntu как единственный способ выпуска Windows-версии.

## 11. Итоговая схема

Принята следующая стратегия:

1. основная разработка ведётся на Ubuntu с использованием OpenAI и AI Factory;
2. сначала создаётся независимое от ОС ядро;
3. сразу после появления рабочего ядра создаётся минимальный Windows-прототип;
4. Windows-интеграция проверяется на раннем этапе;
5. первым законченным продуктом становится Windows MVP;
6. Ubuntu-версия создаётся после Windows MVP на базе общего ядра;
7. финальные сборки выполняются и испытываются в соответствующих целевых ОС.
